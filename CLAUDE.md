# achainsaw

Compiler toolchain for AI agents: AIR (flat SSA IR) text/bytecode -> Cranelift JIT or AOT native code. README.md is the overview for users, and `docs/` the reference.

## Layout
- `crates/achainsaw-ir`: lexer, parser, AST, validator (SSA/type checks), optimizer (`opt.rs`), AIRB codec (`binary.rs`), JSON diagnostics (`diag.rs`).
- `crates/achainsaw-codegen`: Cranelift lowering (`lower.rs`), JIT facade over both backends plus the shared runtime hooks (`jit.rs`), backend selection (`backend.rs`), AOT objects/shared libs (`aot.rs`), CPU feature detection, ISA cap, and Cranelift/LLVM target settings (`cpu.rs`).
- `crates/achainsaw-llvm`: optional LLVM backend (empty without its `llvm` feature): AIR -> LLVM IR (`lower.rs`), ORC LLJIT (`jit.rs`), object emission (`aot.rs`).
- `crates/achainsaw-cli`: `achainsaw` binary (`main.rs`) and the MCP stdio server (`mcp.rs`).
- `crates/achainsaw-py`: PyO3 bindings; type stubs in `achainsaw.pyi`.
- `examples/`: `.air` sources with matching `.airb` bytecode (in `examples/` and `examples/kernels/`; `examples/agent/` holds the README's diagnostic demo, a valid program and its broken copy, with no `.airb`); `tests/`: Python e2e tests.
- `docs/`: the user documentation the README links to: `language.md` (AIR syntax, vector ops, standard library), `parallel.md`, `backends.md` (vector widths, `mm` kernels), `cli.md`, `mcp.md`, `python.md`, `ffi.md`, `kernels.md` (kernel table and NumPy/PyTorch benchmarks, the figure's SVGs) and `llama.md` (single-call decode and prefill, llama.cpp comparisons). New benchmark numbers go there, and into the README's summary table when they change it. `ROADMAP.md` lists planned work; `CONTRIBUTING.md` is for contributors.
- `tests/test_readme.py` runs every `$ achainsaw ...` command in the README's console blocks and compares the output (JSON without timings and thread counts); CI runs it on Linux and macOS. Update the README's output when a command's output changes. The README states only measured numbers (the FAQ's token counts are from the Llama 3 tokenizer in `benchmarks/gguf.py`).
- `benchmarks/`: NumPy and PyTorch comparisons of `examples/kernels/` (PyTorch is optional: each script skips it when it is not installed or with `--no-torch`, and every PyTorch baseline is checked against the case's reference); `gguf.py` (GGUF reader, dequantization, Llama 3 tokenizer) and `llama_model.py` (weight packing for `llama_decode.air`, GGUF conversion, NumPy reference, PyTorch forward pass on its weight-only int4/int8 kernels) back `benchmark_decode.py`, which also runs llama.cpp's `llama-bench` on the same GGUF with `--llama-bench PATH`.

## Commands
- Build: `cargo build --workspace` (release CLI: `cargo build --release -p achainsaw`)
- Rust tests: `cargo test --workspace`
- MCP e2e: `cargo build -p achainsaw && python tests/test_mcp_e2e.py`
- Python binding tests need the extension built first (`maturin develop` or copy `target/*/libachainsaw.so` to `achainsaw.so`), then `python tests/test_py_binding.py` and `python tests/test_gguf_decode.py` (a synthetic GGUF through the loader and `llama_decode.air`). `python tests/test_readme.py` (after `cargo build -p achainsaw`) checks the README's console output.
- Lint (CI): `cargo fmt --all -- --check` and `cargo clippy --workspace --all-targets -- -D warnings`; for Python, `python tools/check_py_types.py` and `mypy` (strict, configured in `pyproject.toml`; needs `pip install mypy numpy`, the versions CI pins).
- Performance (CI's `perf` job on PRs): `python benchmarks/perf_compare.py BASE_DIR HEAD_DIR` runs each checkout's kernel and decode benchmarks (extension at each root) alternately and fails if a result is >25% slower on either backend. An intended slowdown needs the `perf-regression-ok` label, then a re-run of the job.
- LLVM backend (LLVM 22): `export LLVM_SYS_221_PREFIX=/usr/lib/llvm-22`, then add `--features achainsaw/llvm,achainsaw-codegen/llvm,achainsaw-llvm/llvm` to build/test/clippy. Run the suite on LLVM with `ACHAINSAW_BACKEND=llvm cargo test --workspace --features ...`; CI's `test-llvm` job runs it on both backends.

## Git workflow
- Never commit or push directly to `main`. Do work on a feature branch, push it, and open a pull request against `main` (`gh pr create --base main`).
- Make sure `cargo test --workspace` passes before opening the PR.

## Conventions
- Python code is fully typed: every function's parameters and return (`-> None` too), and every variable at its first assignment (`n: int = 0`, `self.rows: int = rows`, or declared in the class body when a method other than `__init__` sets it). Split an unpacked tuple display (`a, b = 0, 1`) into annotated assignments; names bound by loops, comprehensions, `with`/`except`, or unpacking a function's result take their types from it. Use precise types: `npt.NDArray[np.float32]` and the aliases in `benchmarks/gguf.py` (`F32`, `U8`; `Ints`/`Floats` where NumPy's stubs widen an arithmetic result's dtype), `TypedDict`s for fixed-key dicts, `Any` only for JSON, PyTorch tensors (`torch.Tensor`, which is untyped here since PyTorch is optional) and genuinely dynamic values. `tools/check_py_types.py` enforces the variable annotations and `mypy` (strict) the rest; CI's lint job runs both.
- Errors are machine-readable `Diagnostic`s with an `ERR_*` code, span, and `context` for agent self-repair; never plain prose.
- A language change touches lexer -> parser -> validator -> `lower.rs` -> `binary.rs` (AIRB encode/decode) -> `to_air_text`. Regenerate every `.airb` file in `examples/` with `achainsaw assemble` (`crates/achainsaw-ir/tests/vectors.rs` checks they match their `.air` source). There is one AIR language and one AIRB format: no aliases, legacy spellings or older-version decoding, so change the format in place and keep `VERSION` in `binary.rs` as is.
- Vector ops: lane-type rules live in `validator.rs` (`vbin_lane_types`, `VFMA_LANE_TYPES`, `vunary_lane_types`, `VNARROW_LANE_TYPES`, `VSHIFT_LANE_TYPES`, `VPERM_LANE_TYPES`, `VDOT_LANE_TYPES`) and apply to every backend. `vdot` (int8 dot into i32 lanes) uses SVE/NEON `sdot` and x86 VNNI `vpdpbusd` with a sign bias (`(a ^ 0x80)·b − 128·Σb`) on both backends: LLVM through `LowerOptions::int8_dot` (`CpuFeatures::llvm_int8_dot`), Cranelift by emitting the widening trees its ISLE rules fold into `sdot`/`usdot`/`vpdpbusd` (`vdot_part` in `lower.rs`); without them, exact widening sequences. `vdotu` (`VDot::unsigned`, `a` unsigned) is one `vpdpbusd` or `usdot` (FEAT_I8MM, `Int8Dot::arm_i8mm`), and two `sdot`s on Arm without I8MM. Permutations (`VZip`, `VDup`, `vrev`) only move lanes; scalable `vx` lowers them with LLVM's `vector.interleave2`/`deinterleave2`/`reverse` intrinsics since its lane count is unknown at compile time. Conversions (`VUnary`, `VNarrow`) name the result lane type; `VUnaryOp::source_lane` gives the operand's. `vexp` is a fixed op sequence whose constants live in `achainsaw_ir::ast::vexp`, shared by both backends and the reference model, so results are bit-identical. `vfwidenlo`/`vfwidenhi` (suffix = 16-bit source; `VUnaryOp::result_lane` gives f32) and `vnarrow` to f16/bf16 match scalar `fext`/`ftrunc` except NaN payloads: Cranelift and LLVM without hardware support run the shared integer sequences, LLVM with `LowerOptions::native_f16` (x86 F16C, any AArch64) uses `fpext`/`fptrunc`; `half_masked_mm.rs` checks them exhaustively. `CodegenOptions::fast_math` (a compile option, not part of the program: `JitEngine::set_fast_math`, `LowerConfig::fast_math`, LLVM `LowerOptions::fast_math`) switches float min/max to compare-and-select in both backends (`float_minmax` in each `lower.rs`). The optimizer runs before code generation, so `fold_fminmax` in `opt.rs` folds only the cases where both modes agree (`tests/fast_minmax.rs` checks folded == runtime in each mode). `crates/achainsaw-codegen/tests/vector_ops.rs` compiles every op x lane x width for x86_64 (all levels) and aarch64 and checks results against a scalar reference model; extend its `all_kernels()` and `reference()` for new ops. Vector mnemonics are `TokenKind::VOp` so they remain valid register names outside the position after `=`. `crates/achainsaw-codegen/tests/half_masked_mm.rs` covers f16/bf16 conversions (exhaustively, against the `half` crate), `ldm`/`stm` (including a guard-page test that faults on any out-of-bounds access), and `mm` (tolerance-based for floats, exact for i8; every f16/bf16 value through its widening, and a guard-page check that it touches only its matrices). Cranelift's `mm` (`emit_matmul`) runs 4x8 tiles of 128-bit accumulators with scalar edge loops.
- Memory operands carry an optional `Index` (`p[i]`, `p[i:unit]`, in `Load`/`Store`/`MaskedLoad`/`MaskedStore`); both backends compute the address with `mem_addr` before the sandbox check, and AIRB writes an index prefix (`0x30`) before the access. Functions have `rets: Vec<Type>` (`Call::dsts`, `Ret::vals`); host trampolines exist only where `Function::has_trampoline()` (scalars, at most one result). `inline fn` calls are expanded by `achainsaw_ir::inline` in `JitEngine::compile_module`, both AOT paths and `optimize_module`; it merges the copy's entry and single return into the surrounding blocks so straight-line helpers add no branches (every `jmp`/`br` costs a fuel check). Scalar mnemonics added after the reserved ones (`floor` … `ftoui`) are contextual (`Parser::is_contextual_op`); every mnemonic, reserved ones too (`rem`, `min`), is a valid register name outside the position after `=` (`parse_operand`).
- Two backends, one semantics: a language change lowers in both `achainsaw-codegen/src/lower.rs` (Cranelift) and `achainsaw-llvm/src/lower.rs`, with identical results, fuel-check placement, runtime hooks and sandbox checks. Extend `crates/achainsaw-codegen/tests/backend_parity.rs` for new scalar semantics; the rest of the suite runs on both via `ACHAINSAW_BACKEND`. `vx` is 128 bits on Cranelift but 256/512 bits (AVX2/AVX-512) or scalable (`<vscale x ...>`, SVE) on LLVM: tests must size `vx` buffers with `JitEngine::vx_bits()`, and LLVM vector lowering must handle `ScalableVectorValue`s (use the `vec1!`/`vec2!` macros). Scalable code is verified by AOT-compiling for `+sve` locally and by CI's arm64 job (native SVE2 plus a QEMU vector-length sweep).
- LLVM `mm` (`crates/achainsaw-llvm/src/matmul.rs`) dispatches per dtype to AMX, SME, AVX512-BF16 `vdpbf16ps` (bf16) or a vector-FMA kernel from `LowerOptions::matrix`; the caller keeps the sandbox check and fuel charge. The FMA and `vdpbf16ps` kernels run tiles of `TILE_ROWS` rows of C by several vector strips; the FMA kernel first widens a tile's 16-bit/i8 rows of A into a stack buffer (`mm_pack_rows`), since widening and broadcasting each A value from a general register cost as much as the FMAs. bf16 uses AMX/SME/AVX512-BF16 only with `fast_math`, since their bf16 products flush subnormal inputs (`mm_widens_every_half_value_exactly` checks both modes; GitHub's x86 runners sometimes have AMX). `mm_kernels_match_target_matrix_engines` checks the engine choice in assembly; SME and SVE run under QEMU with `tools/qemu-aarch64/run.sh <features> <vector bytes...>` (needs `qemu-user` and the `aarch64-unknown-linux-gnu` Rust target), which links AOT objects into a freestanding harness.
- Both backends keep a function's fuel counter in a register (Cranelift `FuelVar`, LLVM `Fuel`, a stack slot LLVM promotes; each in its `lower.rs`) and write it back around anything that calls out (`calls_out` in each `lower_function`: AIR calls, `alloc`/`free`, `mm`, `par`) and before returns; a new instruction that calls the runtime must be added there. A counter in memory costs a load and store per branch that data stores may alias, which stalled LLVM loops. The fuel slow path calls `rt_fuel_exhausted` through a stub that saves every register (Cranelift: `PreserveAll` `rt_fuel_exhausted_preserve_all`; LLVM on x86-64: `rt_fuel_exhausted_xsave`, called from inline asm, `LowerOptions::fuel_stub`) and continues while the reloaded counter is positive, so loop values are not spilled around it; `parallel.rs::registers_survive_fuel_refills` guards the stubs.
- Quantized weights (`qmat_chunk`, `qmat_chunk4`, `qmat_chunk8`, `qmat_batch` in `std.air`; used by `q4_gemv`, `q8_gemv`, `q4_gemm`, `llama_decode`/`llama_prefill`): 64-row chunks, per 32-block 4 consecutive values of a row per 32-bit lane for `vdotu`, weights unsigned (Q8 stored plus 128, Q4 nibbles 0..15, Q6 0..63; `qmat_block` subtracts bias times the activation half sums), f16 scales widened with `vfwidenlo`, formats 0 Q8_0 / 1 Q4_0 / 2 Q6_K / 3 Q4_K / 4 Q5_K. Q4_K and Q5_K store their values 0..15 / 0..31 with no offset and an f16 scale and min per 32-block (weight s * q - m; the two scale vectors of a block, as Q6_K's): their `qmat_layout` bias is 1, so `qmat_block`'s corrections are the activation sums that `qmat_accm` multiplies by the min. A matrix is a list of parts, 4 words each (weights, scales, format, 64-row chunks), walked by `qmat_layout`, so a fused QKV keeps each part's format (Q4_K_M files store V as Q6_K in some layers); `llama_decode`'s model table holds a pointer per matrix. Keep the bit-plane shifts in `qmat_w5`/`qmat_w6` on i8 lanes: with the groups unrolled, 16-bit lane shifts of the loaded plane crash LLVM 22's VectorCombine on SVE (a scalable load bitcast to another lane size; `Cannot implicitly convert a scalable size`), so AOT-compile for `+sve` after changing them. Quantized activations come with one 16-byte record per 32-block in `dx` (f32 scale, i32 sums of values 0..15 and 16..31, zero), written by `quantize_q8`; buffers and per-token strides of `dx` are 16 bytes per block (`xs / 2` for `xs` activation bytes). Blocks are the outer loop and row strips the inner one, so each block is read in one pass (a strip-outer order strided through whole chunks and fell out of L3). `qmat_batch` runs tiles of 8 tokens (`qmat_chunk8`) when `vl i32` is at least 8, then tiles of 4 (`qmat_chunk4`), then single tokens (`qmat_chunk`); 128-bit vectors (Cranelift, NEON) keep tiles of 4, as 8 tokens' sums spill their 16 registers. The three share their steps as inline functions (`qmat_strip`, `qmat_dots4`/`5`/`6`/`8` and their `x4`/`x8` forms with the groups unrolled, `qmat_w8`/`w4`/`w5`/`w6`, `qmat_dot`/`qmat_dot4`, and for `qmat_chunk8` `qmat_dot1`/`qmat_dot8`; `qmat_acc1`/`qmat_acc2`/`qmat_accm` scale and accumulate in memory on the register steps `qmat_accr`/`qmat_accmr` that `qmat_chunk8` uses, so every kernel's float operations are the same), and `qmat_tiles_match_single_tokens` (`tests/kernels.rs`) calls the tiles directly on every backend and level, since `qmat_batch` never runs `qmat_chunk8` on Cranelift. `qmat_chunk` and `qmat_chunk4` keep two int32 chains per token (values 0..15 and 16..31, added before scaling) and their order of loads and dots: merging the chains or reordering them made Cranelift's prefill up to 19% slower (it neither reschedules loads nor hides the `vdotu` latency with 4 chains). `qmat_chunk8` runs one chain per token (the same integer sum; Q6_K, whose halves have their own scales, runs them one after the other), loops over strips outside blocks so the 8 tokens' f32 sums stay in registers, and has its first strip copy each block's activations and records of the 8 tokens into one 384-byte row (`qmat_prep8`): with 8 token pointers live, LLVM recomputed them in the inner loop. The format is dispatched once per block (once per chunk in `qmat_chunk8`) into a strip loop per format, since Cranelift does not hoist loop-invariant branches so each token's operations are identical: `llama_prefill` must equal `llama_decode` bit for bit (`llama_prefill_matches_decode_exactly`). A layout change touches std.air, `Mat.pack` in `benchmarks/llama_model.py`, the packing in `benchmarks/benchmark_kernels.py`, `Mat::random` in `crates/achainsaw-codegen/tests/llama_decode.rs`, `q_pack` in `tests/kernels.rs`, and `tests/test_gguf_decode.py`.
- Attention: `llama_decode`/`llama_prefill` keep a bf16, head-major KV cache (per layer K then V, each `nkv x ctx x hd` with `ctx` = max_ctx rounded up to 32 by `load_cfg`; V `[nkv x ctx x hd]` written by `to_bf16` after RoPE, K in tiles of 32 positions `[nkv x ctx/32 x hd x 32]` written by `to_bf16_kt`, at the offsets `kv_row` gives) and run flash-decoding on the std functions `attn_split` (one 256-position split of a KV head for its group's query heads, 4 at a time in registers; scores take positions in lanes, a broadcast query value times a K vector per FMA, so they need no horizontal sums, and P V takes V's columns in lanes) and `attn_merge` (also behind `gqa_attention.air`, whose K takes the same tiles). Decode is a `par` over (KV head, split), then one per query head (`attn_out`); prefill runs one task per (tile of 8 tokens, KV head) with each token's splits and merge order (`attn_tok`): the splits every token of the tile sees whole go through one `attn_split` call for all the tile's query heads (each row's arithmetic is independent of its neighbors), the rest per token, which keeps it bit-identical to decode. A cache layout change touches `attn_split` in std.air, `llama_decode.air`, `gqa_attention.air` and its packing in `benchmarks/benchmark_kernels.py` and test in `tests/kernels.rs`, `Model.new_cache`/`cache_kv` in `benchmarks/llama_model.py`, `Model::cache_len`/`cache_at` in `crates/achainsaw-codegen/tests/llama_decode.rs`, and `tests/test_gguf_decode.py`. The f64/NumPy references round K and V from their own values, so a value at a bf16 rounding boundary can land one step apart and flip an int8 quantization downstream: those tests allow 1e-2 of the hidden state's scale.
- Register names are scoped by dominance (`achainsaw_ir::names`): a definition shadows an earlier one of the same name in the code it dominates (`loop(i)` then `body(i)`, `i = add i, 1:i64`), and `check_reaching_definitions` in `validator.rs` rejects a use that two definitions can reach (`ERR_AMBIGUOUS_REGISTER`). `names::unique_names` renames shadowing definitions apart, and both inlining entry points (`inline_module`, `inline_in_place`) run it first, so the inliner, the optimizer and both backends see each name defined once; new passes that run before them must not assume unique names.
- Long-running bulk ops must charge fuel in the JIT via `rt_consume_fuel` (see `emit_matmul` in `lower.rs`) so MCP's sandbox still stops runaway programs.
- MCP `air_run` runs code under `JitEngine::enable_sandbox`: `alloc` draws from a private arena, every memory access is bounds-checked against it (`emit_bounds_check` in `lower.rs`; `mm` via `rt_sandbox_check_mm`), `free` must name a live allocation, and function entry checks stack depth. New instructions that touch memory must call the guard, and `crates/achainsaw-codegen/tests/sandbox.rs` must cover them; violations surface as `ERR_MEMORY_VIOLATION` / `ERR_STACK_OVERFLOW`, never a crash.
- `par n, f(args)` (fork-join): `rt_par_for` in `jit.rs` runs `f`'s scalar trampoline on the calling thread plus a spin-then-park helper pool (`ACHAINSAW_THREADS`); AOT lowers it to a serial loop. Dispatch is lock- and allocation-free: the `ParRegion` lives on the caller's stack, and helpers reach it only by joining through the `ParPool::joined` word (`par` number, closed bit, count), which the caller closes and waits to drain before returning; keep fields every index writes on their own cache lines (`CachePadded`). Workers count fuel in their own counters drawn from the caller's budget, so modules that use `par` load their counter on function entry (`rt_fuel_counter`); others keep the constant address. New runtime state that JIT code reads must be per thread or shared safely; `crates/achainsaw-codegen/tests/parallel.rs` covers results, fuel accounting and failures in workers.
- Standard library: AIR functions in `crates/achainsaw-ir/std/std.air`, linked into a module by a top-level `use name, ...` when it is parsed (`stdlib::link`, called from `Parser::parse_module`), with the library functions they call. Every function needs a `#` comment directly above it (its documentation for `achainsaw std` and MCP `air_std`; `stdlib` tests check it). Kernels in `examples/` import shared code from it instead of copying (`llama_decode`, `q4_gemv`, `q8_gemv`), so their tests cover it.
- `SERVER_INSTRUCTIONS` in `crates/achainsaw-cli/src/mcp.rs` is the AIR primer shown to MCP clients (Claude Code, Claude Desktop). Update it when syntax changes; `test_server_instructions_example_is_valid_air` JIT-runs its example.
- New MCP tools: add a `handle_*` function, a `get_tools_list` entry, a `tools/call` match arm, and a unit test.
- `.mcp.json` registers the local MCP server for Claude Code in this repo.
- Vector ISA work: test lower tiers on one machine with `--isa <level>` or `ACHAINSAW_MAX_ISA` (`sse`, `avx`, `avx2`, `avx512`, `amx`, `neon`, `sve`, `sve2`, `sme`); in tests use `JitEngine::with_features(&CpuFeatures::host().capped(level)?)` since the cap is process-global. Cranelift's generic `x86-64-v3`/`v4` presets omit `has_avx`, so always configure ISAs through `cpu.rs` (it completes feature prerequisites).
